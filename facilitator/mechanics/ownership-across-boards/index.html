Ownership across boards

Two teams storm two slices of the same business. Both walls end up with an event called “Payment authorized”. Both teams enrich it. One writes the topic payment/authorized/v1/{orderId}/{paymentId}; the other writes auth/completed/v1/{orderId}/{paymentId}.

Nothing is broken - this is what parallel work looks like. But only one of those can be the event in Event Portal, and choosing between them is a decision for the room, not for a tool. What the tool owes you is the noticing.

How ownership is decided

Section titled “How ownership is decided”

An event is identified by its name, normalized. There is no hidden lineage ledger tracking which copy came from where, deliberately: Event Portal resolves by name too, and a second source of truth is a second thing to keep honest.

Ownership resolves in this order:

  1. A ★ claim on a flow board. Starring an event is a team saying “we define this one”.
  2. The map seat. If nobody claimed it, the domain lane it was seated into on the map is the prediction of record.
  3. First use, alphabetically. A fallback that comes with a loud warning, because it is a coin toss, not a decision.

The owner’s enrichment is the canonical contract: its topic, schema and QoS. Other copies are never quietly merged in.

What the review tells you

Section titled “What the review tells you”

Open ✓ review on the map. Above the map’s own checks you get findings that compare boards against each other - no single board can see these:

FindingWhat happened
Ownership conflicttwo or more boards claim ★ the same event
Seated in one domain, claimed by anotherthe map predicted one owner, a different board claimed it
Same event, different contractagreed owner, but another board’s topic, schema or QoS disagrees
Shared event missing from the mapseveral boards use it, the map never heard of it
Shared event nobody ownsused across boards, claimed by none
Near-duplicate event namestwo names one small edit apart - usually one event, spelled twice
Map events never picked upcoarse events on the map that no board ever stormed, reported together
Will export shared (via system)an application in one domain touches other domains’ events, so the export must mark them shared - one finding per application, listing the events

An event that several boards use healthily is not a finding. It shows on the ⇄ badge and in the panel, because a state that asks the room for no decision does not belong in a list of things to fix.

Resolving a conflict in the room

Section titled “Resolving a conflict in the room”

An ownership conflict lists every claiming board with its contract, and offers claim ownership for this board per claimant. Choosing one:

  • un-stars every other board’s claim, so exactly one team defines the event;
  • aligns the other boards’ contracts to the winner’s, filling only the fields the winner has actually set.

You see the diff before it commits. Divergence is surfaced, never auto-fixed: which topic spelling is right is exactly the conversation the workshop exists to have, and a tool that quietly picks one has skipped it.

If a losing board is finalized, its ★ cannot simply be dropped: a claim is storming content, and finalizing freezes that. The preview says so before you commit, plain confirm is offered only for the boards that can change now, and reopen and transfer does the whole thing - unlocks each finalized board, moves the claim, and locks it again afterwards, even if something fails midway. Contract alignment never needs this: enrichment stays editable on a finalized board.

Seated in one domain, claimed by another is the same question with the map on one side, so it resolves both ways from the card:

  • re-seat to <domain> moves the map’s seat to the board that actually claimed the event - the map follows practice. This one is an ordinary change on the map you have open, so ⌘Z covers it.
  • claim for <board> (the seat) gives the claim to the board the map predicted, starring it if it never claimed and un-starring the other - practice follows the plan.

If the seated board has no copy of the event at all, only the re-seat is offered: claiming for a board that never stormed the event would invent ownership.

One caveat before you click. The claim transfer, the align-to-owner fix, and the “add to map” fix on a flow board all write to a board you do not currently have open, so none of them can be undone with ⌘Z - reversing one means going to that board and editing it directly.

Triaging the list

Section titled “Triaging the list”

Every finding takes a status, and not an issue has a one-click button of its own next to the dropdown, because a cross-board rule can be right about the shape and wrong about this workshop. Two chip rows narrow the register and each picks exactly one option: priority (all, high, med, low) and status (open, deferred, resolved, any), starting on open.

Where flow boards feel it

Section titled “Where flow boards feel it”

Two things appear on a flow board once the workshop has a map with events:

  • The owner’s contract, as a reference. When you enrich an event another board owns, the panel shows their contract and offers use the owner’s contract - which just writes an ordinary enrichment, so nothing special happens to the log.
  • Event name suggestions from the map’s registry as you type, which is the cheapest possible cure for near-duplicates.

A workshop with no map (one created before maps existed) sees neither, and no ownership findings. That is intended: those checks need a catalog to compare against, and inventing one would be worse than staying quiet.
