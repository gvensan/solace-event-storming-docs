From the wall to Event Portal

translation map · for the architects who receive the export

The workshop's finished wall becomes an Event Portal import file - downloaded and loaded through EP's own UI, or pushed straight into a tenant from the same toolbar (one board, or the whole workshop from the map). Either way the artifact is identical. Every design object in it traces back to something the room agreed on - this sheet is the dictionary, including what deliberately does not cross over.

What becomes what

Applications come from the system attribute - never from a command or a policy sticky. An event answers "who emitted this?"; a policy answers "whose code reacts?". Both answers are system tags, and only system tags become Applications.

The board itself "Payments & Wallet" - one board is one slice of the business
→
Application Domain exactly one per board, named "WORKSHOP: Board" so a workshop's domains group together
Context boundary ⬚ the split INSIDE the board, plus its pitch
→
Description text not a domain - contexts are an intra-board split, so they ride in the domain's description and as "Context:" lines. Draw them anyway: that description is how the domain explains itself
System attribute on ANY sticky - event, policy or command
→
Application a vendor or external participant, tagged with the context most of its stickies live in (majority vote; a spread earns a warning)
Aggregate "Trip", "Reservation" - the thing it happened to
→
Application (internal) your own service, not a vendor: it publishes the events grouped into it and consumes through the policies grouped into it. This is what gives an internally-emitted event a publisher at all
Domain event "Payment authorized"
→
Event + Event Version QoS intent and owning team ride along in the description - EP has no first-class fields for them
Resolved topic acme/air-res  +  payment/authorized/v1/{tripId}
→
Topic address three levels compose it: the workshop root (the customer's naming space, set once for every board) + the board sub-root + the relative path typed on the sticky. Each segment becomes an address level; {placeholders} become variable levels, the rest literal
Schema sketch field list or JSON sample
→
Schema + Schema Version coerced to valid JSON Schema; an event without one imports with a "schema TBD" marker, never blocked
System on the event who emits "Payment authorized"
→
Publish relation the emitter attribute declares the publisher - independent of any command. An event grouped into an aggregate is published by that aggregate too, marked as ownership rather than emission
Event → policy link + the policy's own system "...triggers On payment, notify" · run by Billing
→
Subscribe relation The policy is the handler, not the application - its system is who runs it, and that application becomes the subscriber. No system on the policy = no subscribe relation (the export warns, and Board Review flags it). Relations come only from links the room accepted, never from layout.

Why publishing needs one tag and subscribing needs two. Being emitted by X is a property of the event, so the event's own tag settles it. Being consumed is not a property of the event at all - it is a decision somebody made. The policy is the record of that decision; its system is who acts on it. (Read models consume nothing in EP: only event→policy links produce subscribe relations.)

What stays workshop-side, on purpose

Actors and read models - they answer "who decides, using what"; EP models systems, not people.

Commands - service entry points for your design docs; EP's catalog is events.

Hotspots and their decisions - exported as the workbook's Hotspots & Decisions sheet: the organization's decision backlog.

Plan tags (build owner, now/next/later) - delivery commitments are workshop exhaust, not architecture.

Votes, chat, history - the room's process; replayable in the tool from the board file.

One workshop, several boards

Export the workshop, not just the board. A workshop usually storms several domains, and the same event shows up on more than one wall. The map board offers Event Portal file (multi-domain: workshop, merged): one domain per board, and one event per name, homed in the board that owns it - a ★ claim first, then the domain it was seated in on the map. The owner's topic, schema and QoS become the contract; where another board disagrees, the file warns instead of quietly picking. Sharing is derived from actual use across boards, so the import shows reuse rather than five copies of "Payment authorized".

Everything imports as DRAFT. The workshop proposes; your Event Portal governance disposes. Review each object before promoting - the file is a faithful record of the room, not a decree.
