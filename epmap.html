From the wall to Event Portal

translation map · for the architects who receive the export

The workshop's finished wall exports as an Event Portal import file you load through EP's own UI. Every design object in that file traces back to something the room agreed on - this sheet is the dictionary, including what deliberately does not cross over.

What becomes what

Applications come from the system attribute - never from a command or a policy sticky. An event answers "who emitted this?"; a policy answers "whose code reacts?". Both answers are system tags, and only system tags become Applications.

Context boundary ⬚ "Payments & Wallet" + its pitch
→
Application Domain named "WORKSHOP: Context" so one workshop's domains group together; the room's pitch becomes the description
System attribute on ANY sticky - event, policy or command
→
Application homed in the domain most of its stickies live in (majority vote; a spread earns a warning)
Domain event "Payment authorized"
→
Event + Event Version QoS intent and owning team ride along in the description - EP has no first-class fields for them
Resolved topic root/payment/authorized/v1/{tripId}
→
Topic address each segment an address level; {placeholders} become variable levels, the rest literal
Schema sketch field list or JSON sample
→
Schema + Schema Version coerced to valid JSON Schema; an event without one imports with a "schema TBD" marker, never blocked
System on the event who emits "Payment authorized"
→
Publish relation the emitter attribute declares the publisher - independent of any command
Event → policy link + the policy's own system "...triggers On payment, notify" · run by Billing
→
Subscribe relation The policy is the handler, not the application - its system is who runs it, and that application becomes the subscriber. No system on the policy = no subscribe relation (the export warns, and Board Review flags it). Relations come only from links the room accepted, never from layout.

Why publishing needs one tag and subscribing needs two. Being emitted by X is a property of the event, so the event's own tag settles it. Being consumed is not a property of the event at all - it is a decision somebody made. The policy is the record of that decision; its system is who acts on it. (Read models consume nothing in EP: only event→policy links produce subscribe relations.)

What stays workshop-side, on purpose

Actors and read models - they answer "who decides, using what"; EP models systems, not people.

Commands - service entry points for your design docs; EP's catalog is events.

Hotspots and their decisions - exported as the workbook's Hotspots & Decisions sheet: the organization's decision backlog.

Plan tags (build owner, now/next/later) - delivery commitments are workshop exhaust, not architecture.

Votes, chat, history - the room's process; replayable in the tool from the board file.

Everything imports as DRAFT. The workshop proposes; your Event Portal governance disposes. Review each object before promoting - the file is a faithful record of the room, not a decree.

Companion artifacts: the workbook (spreadsheet of everything), the architecture diagram (SVG of applications and events), and the board file (reopen the session later, history intact). See the handoff sheet.
